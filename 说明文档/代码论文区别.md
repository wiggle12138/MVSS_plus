# 代码-论文差异说明（MVSS）

- MVSS = 基于多版本状态同步的跨分片账户迁移
- 核心 = 协同调度 + 多版本同步

---

## 1. 差异总览

| 论文/设计要点 | 当前代码状态 | 结论 |
|---|---|---|
| 交易分流而非整体锁定 | 有分流能力，但仍大量使用锁池与锁标记 | **部分实现** |
| 老/新交易按时间协同执行 | 使用 `TXmig1_Time` 与 `RequestTime/Second_RequestTime` 做分界 | **部分实现** |
| 新交易重定向到目标分片 | 用 `IsRelay`/`Relay_Lock` + relay 流程表达 | **部分实现** |
| 多轮 `TX_sync` 状态桥（v1->v2 循环） | 无 `TX_sync` 消息类型与往返握手协议 | **未实现** |
| 交错时间戳下“暂停老交易、同步后继续” | 无显式“暂停-同步-恢复”状态机 | **未实现** |
| 源分片 nonce 防双花 | `Transaction` 无 nonce，`AccountState` 的 nonce 注释掉 | **未实现** |
| 目标分片“重定向标签+nonce”防重放 | 无独立重定向标签字段，无标签+nonce 联合校验 | **未实现** |

---

## 2. 与你第1点（交易分流处理，而非锁定）的差异

### 2.1 设计目标（你给出的）

- 不锁交易，按迁移时刻把交易分成老/新两类。
- 源分片处理老交易，目标分片处理新交易。
- 新交易到源分片后打重定向标签并转发到目标分片。

### 2.2 当前代码实现

1) **确实有“按时间分流”机制**  
在 `core/txpool.go` 的 `FetchTxs2Pack` / `LockTX`，会使用：

- `TXmig1_Time < RequestTime`（发送方侧）
- `TXmig1_Time < Second_RequestTime`（接收方或 relay 侧）

来判定交易进入哪个执行路径。

2) **但实现仍以“锁池”作为核心调度手段**  
代码存在并大量使用：

- `Not_Locking_TX_Pools`
- `Locking_TX_Pools`
- `Outing_Before_Announce_TX_Pools`

以及 `SenLock`、`RecLock`、`HalfLock`、`LockTime` 等字段。  
即使 `Not_Lock_Acc_When_Migrating=true`（注释为多版本并发），本质仍是“分流 + 挂起池”。

3) **新交易重定向是“隐式标签”而非“显式标签”**  
当前主要靠：

- `Transaction.IsRelay`
- `Transaction.Relay_Lock`
- 分片映射 `Account2Shard`

组合表达“重定向语义”，没有单独的“重定向标签”数据结构或签名字段。

### 2.3 差异结论

- 代码不是“完全不锁”，而是“带锁池的分流执行”。
- 与论文“分流替代锁定”的纯粹表达有偏差。

---

## 3. 与你第2点（多版本状态同步 TX_sync 循环桥梁）的差异

### 3.1 设计目标（你给出的）

交错时间戳场景（老-新-老）下，要求：

1. 源分片暂停后续老交易；  
2. 先提交前段老交易，生成版本1；  
3. 通过 `TX_sync` 发目标；  
4. 目标执行新交易得到版本2；  
5. 再 `TX_sync` 回源；  
6. 源继续执行剩余老交易；  
7. 可循环往复，保证全局时间顺序。

### 3.2 当前代码实现

1) **没有 `TX_sync` 协议实体**  
`pbft/cmd.go` 中没有 `cTX_sync`；类型里也无 `TX_sync`。  
迁移相关消息是：

- `cTXmig1`（实际载荷 `Mig2`）
- `cAnnounce`
- `cCaP`（ChangesAndPendings）
- 停机路径的 `cBalanceAndPending`

2) **没有显式“交错检测后暂停并同步再恢复”的状态机**  
未看到按“时间戳交错事件”触发的：

- pause old tx
- sync out
- sync back
- resume old tx

这类流程控制变量/消息握手。

3) **当前更像“一次迁移流水线 + pending补偿”**  
主路径是：

- `TXmig1 -> TXmig2 -> Announce -> ChangesAndPendings/TXns`

可完成迁移期状态收敛，但不等价于论文定义的“多轮版本桥梁同步协议”。

### 3.3 差异结论

- 当前代码具备“跨片状态传递能力”，但不具备论文语义中的“可循环 TX_sync 双向版本同步机制”。
- 因此在复杂交错场景下，与论文的顺序保证方式并不一致。

## 4. 与你第3点（安全防护：防双花/防重放）的差异

### 4.1 防双花（nonce）

- `core/transaction.go` 的 `Transaction` 无 nonce 字段。
- `account/account_state.go` 中 `AccountState` 的 `Nonce` 是注释状态。

**结论**：未形成“每个 nonce 仅成功一次”的执行约束，和论文描述不一致。

### 4.2 防重放（重定向标签 + nonce）

- 当前无独立“重定向标签”字段与验证逻辑。
- 主要依赖 `IsRelay/Relay_Lock` 与分片归属逻辑做流程分发。

**结论**：缺失“标签 + nonce”联合校验闭环，与论文安全模型存在明显差距。

---

## 5. 造成差异的直接原因（从工程形态看）

1. 当前代码目标偏“可运行仿真与实验统计”，采用了较多工程化简化。  
2. 共识路径以单节点快速提交为主，复杂跨片同步协议没有完全产品化。  
3. 迁移方案并存（全锁/不锁/半锁/停机），导致语义与论文主线被混合。  
4. 安全字段（nonce、显式标签）未进入交易与状态主数据结构。

---

## 6. 结论（可直接用于论文与代码对齐说明）

当前仓库已经实现了 MVSS 的“部分核心思想”：  

- 有迁移期交易分流；
- 有跨片状态/交易传递；
- 有基于时间戳的老新划分。

但与论文定义仍存在三类关键缺口：

1. **分流不彻底**：仍大量依赖锁池机制；  
2. **同步不闭环**：缺少显式 `TX_sync` 双向多轮协议；  
3. **安全不完备**：无 nonce 防双花、无显式标签+nonce 防重放。

因此，当前代码更准确定位应为：  
**“MVSS 思想驱动的工程近似实现（prototype）”，而非论文机制的严格等价实现。**
