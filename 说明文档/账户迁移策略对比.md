# 账户迁移策略对比（MVSS vs 基线）

本文说明本仓库**策略对比实验**中三种账户迁移方法的区别、控制变量设计，以及与 LB-Chain 的关系。实验配置与 `-m` 参数见 [参数配置.md](./参数配置.md)。

---

## 一、实验要回答的问题

本文创新点在 **账户迁移过程本身**（迁移期如何处理 pending / 新到达交易、如何保持跨分片一致性），而不是在 **「如何把账户分到各分片」** 这一层。

因此对比实验应固定：

- 跨分片执行路径：**Relay**（Monoxide 式中继 + Merkle 证明，本仓库 `TryRelay` / `handleRelay`）；
- 账户重分配算法：例如 **CLPA**（或统一固定为 PageRank，见 `PorC`）；
- 触发时机、块大小、注入速率等链参数（见 `参数配置.md` §三）。

**唯一变化量**：迁移触发后，源/目标分片在 **TXmig1 → TXmig2 → Announce → 收尾** 阶段采用的 **账户迁移策略**。

---

## 二、控制变量逻辑

你的理解是对的，可概括为：

```text
固定：Relay 跨分片 + CLPA（或固定 PorC）重分配 + 相同负载/链参数
变化：迁移期内三种策略（SOTA-Lock / Fine-tuned-Lock / MVSS）
```

| 层次 | 是否作为对比变量 | 说明 |
|------|------------------|------|
| 账户重分配（CLPA / PageRank 等） | **否，应固定** | 决定「谁迁到哪」；LB-Chain 的 LSTM+热点分配属于另一研究线，不是 MVSS 论文主线 |
| 跨分片交易执行（Relay） | **否，应固定** | 三种策略共用同一 relay 栈 |
| 迁移期交易调度与状态同步 | **是** | SOTA-Lock / Fine-tuned-Lock / MVSS 的差异所在 |

### 与 LB-Chain 的关系

**LB-Chain**（Li et al., IEEE TPDS 2023）的主要贡献包括：

- 负载预测与 **账户分配算法**（LSTM、热点账户迁移）；
- 独立的 **Account Migration Transaction**、源片队列转发、目标片验证推迟、迁移交易高优先级等。

其中 **账户重分配方案** 不是本文 MVSS 要对比的创新维度；若实验只关心「迁的过程中怎么锁/怎么分流/怎么同步」，则：

- LB-Chain 在迁移**执行语义**上更接近「迁移期间关联交易大量挂起、等迁移完成再处理」的 **全锁** 思路；
- 本仓库用 **`-m SOTA-Lock`** 实现 Fine-tuned Lock 论文中的 **SOTA Lock** 全锁基线，**不单独实现 LB-Chain 协议**；
- 论文表述上：全锁基线写 **SOTA Lock**（或注明「与 LB-Chain 类全锁迁移语义对照」），不宜把 `SOTA-Lock` 直接等同于 LB-Chain 全文系统。

## 三、三种策略在迁移过程中的区别

三种方法在工程上共用 **BlockEmulator 迁移流水线骨架**（`TXmig1` → `TXmig2` → `Announce` → `CaP`/pending 搬运），差异集中在 **迁移窗口内对交易的处置**。

### 3.1 总览表

| 维度 | SOTA-Lock | Fine-tuned-Lock | MVSS（本文） |
|------|-----------|-----------------|--------------|
| 代码 `-m` | `SOTA-Lock`（ lock） | `Fine-tuned-Lock`（finetuned） | `MVSS` |
| 核心思想 | 迁出账户 **状态 + 全部关联交易** 一并锁住 | **只锁 Payer**（扣款方），Payee 可继续 | **不整链锁池**；按时间 **老/新分流** + 重定向 + TX_sync |
| 迁出方 sender 交易 | 进 `Locking_TX_Pools`，暂停打包 | `Outing_Before_Announce` 半锁，暂停 Payer 侧 | 老 tx 继续打包；**新 tx 重定向**到目标分片 |
| 迁出方 recipient 交易 | **同样锁住** | 可继续（含 relay 入账） | 老 tx 继续；新到达经 relay/重定向 |
| 迁移期吞吐 | 低（锁池大） | 中（优于全锁） | 高（目标：少挂起、少锁） |
| 一致性手段 | 锁 + Announce 后 CaP | 半锁 + 修改 relay 语义 + CaP | nonce + RedirectTag + TXsync（Phase1）/ Delta（Phase2） |
| 与论文对应 | FTL 论文 SOTA Lock | Huang INFOCOM'24 Fine-tuned Lock | TrustCom / 期刊 MVSS 主线 |

### 3.2 SOTA-Lock（全锁基线）

**机制（迁移触发后）：**

1. `TXmig1` 上链时：`Lock_Acc[addr]=true`，初始化 `Locking_TX_Pools[addr]`。
2. 凡涉及该账户的 **sender 或 recipient** 的交易，在入池或打包时被拦入锁池，**不参与正常出块**。
3. 部分接收方被锁交易标记 `IsRelay`，走跨分片 relay。
4. Announce 后通过 `CaP` 将 pending 批量发往目标分片。

**特点：**

- 实现简单，安全性直观（迁移完成前不执行关联 tx）。
- **关联交易的 makespan 长**（Fine-tuned Lock 论文的主要批评点）。
- 对应「全锁定」类 baseline；**不是** LB-Chain 的 migration-tx + 推迟验证协议，但实验角色上可作为 **全锁对照组**。

### 3.3 Fine-tuned-Lock（半锁基线）

**机制（迁移触发后）：**

1. `TXmig1` 后：`Outing_Acc_Before_Announce[addr]=true`，Payer 侧交易进入 `Outing_Before_Announce_TX_Pools`。
2. **仅锁定 sender 为迁出账户** 的非 relay 交易（Payer TX）；收款方相关交易在规则允许下 **仍可执行**（`HalfLock` 等标记配合状态更新）。
3. Announce 前后分 **Before / After** 两阶段搬运 pending；relay 路径针对迁移期安全做了适配。
4. 目标分片通过 `TXmig2` 接管账户后继续处理积压。

**特点：**

- 在 **不牺牲迁移安全** 的前提下，降低对 Payee 的阻塞，论文报告 makespan 优于 SOTA Lock 约 30% 量级。
- 本仓库 `-m Fine-tuned-Lock` **可直接用于实验**，与 BlockEmulator Fine-tune-lock 分支同源思路。

### 3.4 MVSS（本文方法）

**机制（迁移触发后，`IsMVSS()` 分支）：**

1. **无 `Lock_Acc` 整账户锁池**；迁出账户标记 `Not_Lock_Acc`，但行为是 **分流** 而非挂死队列。
2. **老交易**（`RequestTime ≤ TXmig1_Time`）：源分片继续打包执行。
3. **新交易**（迁移后到达）：源分片 **`mvssRedirectNewTx`** 打 `RedirectTag` + nonce，TCP 转发至目标分片，**不进源分片队列**。
4. 目标分片校验 RedirectTag + nonce，防重放；迁入后由 `TXmig2` / Announce 完成归属切换。
5. 若时间戳 **old-new-old 交错**：`DetectInterleave` 触发 FSM 暂停部分老 tx，经 **`TXsync`**（`-m MVSS`）或 **`TXsyncDelta`**（`-m MVSS-Delta`）在源/目标间桥接状态；Delta 校验失败时直接 abort。
6. Announce 后仍可有 CaP 收尾，但核心不再依赖「锁死全部关联交易」。

**特点：**

- 创新点是 **迁移期协同调度 + 多版本/增量状态同步**，而非换 CLPA 或换 relay。
- 预期：**更低锁定率（RLT）**、更短迁移期关联延迟；Phase2 `MVSS-Delta` 进一步降低 sync 带宽。

## 四、迁移时间线（概念对齐）

三种策略在「客户端下发新映射 → 各分片 `handleNewMap` → 多轮出块完成迁移」时间轴上，差异集中在 **斜线区域**：

```text
时刻 ──────────────────────────────────────────────►

     [重分配结果下发]     [TXmig1]    [TXmig2/Ann]    [迁移完成]
            │                │            │              │
  CLPA      ├────────────────┴────────────┴──────────────┤  ← 固定（非对比变量）
  Relay     ├────────────────────────────────────────────┤  ← 固定

  SOTA      │████████ 全锁关联交易 ████████│  CaP 收尾   │
  Finetuned │████ Payer锁 ████│ Payee可走 │  CaP 收尾   │
  MVSS      │老tx执行│新tx重定向│ TXsync │  目标片消化  │
```

## 五、本仓库如何跑三组对比

固定参数示例（详见 [参数配置.md](./参数配置.md)）：

```text
PorC=CLPA, MigrateBeforeInject 按实验设定统一,
Inject_speed / MaxBlockSize / Max_Commit_Block 一致,
扩展场景开关全部 off
```

| 组别 | 命令 |
|------|------|
| MVSS | `start_2shard_2node.bat selectedTxs_300K.csv MVSS` |
| Fine-tuned-Lock | `start_2shard_2node.bat selectedTxs_300K.csv Fine-tuned-Lock` |
| SOTA-Lock | `start_2shard_2node.bat selectedTxs_300K.csv SOTA-Lock` |

读日志时关注：`locked_txs`、迁移阶段延迟、队列长度、`S*_mig*.csv` 与 `S*_block.csv` 中 relay/正常 tx 比例。

## 六、小结

| 问题 | 结论 |
|------|------|
| 控制变量是否应为「同 relay + 同 CLPA，只换迁移策略」？ | **是**，这是对比 MVSS 与两条锁基线的正确做法。 |
| LB-Chain 的账户重分配创新是否本文重点？ | **不是**；重分配层应固定，避免与迁移策略混淆。 |
| 全锁 baseline 用谁？ | 本仓库 **`SOTA-Lock`**（SOTA Lock），不是 LB-Chain 完整协议。 |
| 半锁 baseline 能否直接实验？ | **能**，`-m Fine-tuned-Lock`。 |
| 本文方法 | **`-m MVSS`**（后续 `-m MVSS-Delta` 为同策略 + 增量 sync）。 |
