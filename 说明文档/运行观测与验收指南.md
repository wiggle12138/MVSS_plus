# 运行观测与验收指南

统一「单次联调应看到什么」与「批量实验如何验收」。  
适用：`start_2shard_2node*.bat`（联调）；`run_exp1.bat` / `run_exp2.bat` / `run_exp4.bat` / `run_exp6.bat`（批跑）。

---

## 1. 运行前参数可触发性检查（先做）

在本系统里，“达到迁移阈值”不是只看 `MaxInjectTxs` 和 `MaxBlockSize`，而是由 **client 收到的分片回复次数** 驱动。

### 1.1 关键触发逻辑（代码语义）

1. client 初始化阈值计数器：
   - `max_commit_block = Max_Commit_Block * Shard_num`
2. 每收到一次分片 `cReply`，计数器 `max_commit_block--`。
3. 当 `max_commit_block <= 0` 且有交易可遍历时，才会在 client 侧触发：
   - `每个分片出X啦！`
   - `发送MigrateWanted`

> 实践上可理解为：至少要让系统持续到“每分片约 `Max_Commit_Block` 个出块”的时间窗口，且该阶段仍有交易活动。

### 1.2 运行前粗估公式（用于避免“跑了但不迁移”）

给定：

- `Block_interval`（秒，默认 2）
- `Inject_speed`（每秒注入速率，代码按每 2 秒注入 `2*Inject_speed`）
- `Max_Commit_Block`（每分片触发阈值，默认 20）

粗估注入持续时间：

```text
T_inject ≈ MaxInjectTxs / Inject_speed
```

迁移触发时间尺度（每分片）：

```text
T_trigger ≈ Max_Commit_Block * Block_interval
```

建议至少满足：

```text
T_inject >= T_trigger
```

默认参数下（`Inject_speed=400`, `Block_interval=2`, `Max_Commit_Block=20`）：

- `T_trigger ≈ 40s`
- 所需 `MaxInjectTxs` 约 `>= 16000`（建议留余量用 `20000`）
- 若 `MaxInjectTxs=5000`，`T_inject≈12.5s`，高概率不会进入重配置阶段

### 1.3 一次运行是否具备“可验收前提”

先在 `client.out.log` 看三条：

1. `每个分片出20啦！`
2. `正在向分片S*的主节点发送MigrateWanted消息`
3. `所有分片都发送了pending！`

若这三条未出现，本轮不要做 Stage3/窗口敏感性结论，先调整注入规模或触发阈值参数。

## 3. 正常全流程（期望现象）

### 阶段 A：启动与注入

1. `client.out.log` 出现：
   - `SyncProbe enabled ...`（开探针时）
   - `成功读取 ... 笔交易`
   - `InjectStartTx ... MaxInjectTxs ...`
2. `S0_N0.out.log` / `S1_N0.out.log` 出现：
   - `首块等待交易注入后再出块`
   - 之后连续 `propose1` 出块

### 阶段 B：达到迁移触发阈值

1. `client.out.log` 出现：
   - `每个分片出20啦！`（默认 `Max_Commit_Block=20`）
   - `发送MigrateWanted`
2. 随后出现：
   - `所有分片都发送了pending！`
   - `次数：1 时间：...`（本轮重分片耗时）

### 阶段 C：探针注入（开启时）

1. `client.out.log`：
   - `PhaseA ... ids=...1,...3`
   - `PhaseB ... id=...2`
2. `S0_N0.out.log`：
   - `NewMap 后提前 Pause suffix-old`
   - `源片 ... prefix old 就绪，发送 State_ini sync`
3. `S1_N0.out.log`：
   - `收到分片 S0 的 TXsync`
   - `SyncProbe Ingress tx=...2 ... 本片入池`

### 阶段 D：收敛与停止

1. `client.out.log`：
   - 注入完成后继续出块
   - 出现 `每个活跃分片已连续 5 个空块 ... 停止系统运行`
2. 节点日志：
   - `节点收到终止节点消息，停止运行`

## 4. 固定验收链路（每次都做）

### 链路 1：sync 通信闭环（探针开启）

检查 `log/S0_sync.csv`、`log/S1_sync.csv`：

期望闭环：

1. 源片 `S0_sync.csv` 有 `send,sync`
2. 目标片 `S1_sync.csv` 有 `recv,sync` + `apply,sync`
3. 目标片有 `ack_send,sync`
4. 源片有 `ack_recv,sync`

若停在 `send/recv/apply`，说明 Stage3 未完成闭环。

### 链路 2：探针交易落块

检查 `log/S0_transaction.csv`、`log/S1_transaction.csv`：

- 期望：探针 1/3 在 `S0_transaction.csv`
- 期望：探针 2 在 `S1_transaction.csv`
- 常用 probe id：`9000000001/2/3`、`9000000011/12/13`、`9000000021/22/23`

若全部搜不到，说明探针交易未被打包上链（可能卡在队列或被过滤）。

## 5. 常见故障模式与定位

### 故障 A：`sync.csv` 无 `ack_send/ack_recv`

现象：

- `S0_sync.csv` 只有 `send`
- `S1_sync.csv` 只有 `recv/apply`
- transaction 中无 probe tx 上链

常见根因（MVSS 全量 sync 当前实现）：

1. `TXsync` 先于 `TXmig2` 到达目标片
2. 目标片 `apply` 时尚未建立 `MigCtx`，无法进入后续 ack 逻辑
3. 后续 `handleMig2` 建立 `MigCtx(FSM=WaitSyncIni)`，探针 tx2 卡在队列里不上链

日志特征：

- `S1_N0.out.log` 先看到 `收到 TXsync` / `apply`
- 很后面才看到 `接收到迁移请求`（`TXmig2`）
- 最终 `Queue_len=3` 持续多块（常对应 3 笔 probe tx2）

### 故障 B：probe tx2 到达太早

现象：

- tx2 在目标片过早处理，`PendingSyncAck` 不置位
- 可能出现 Stage3 卡死

优先检查：

- `SyncProbePhaseBDelayMs` 是否过小
- 目标片是否已完成 `handleMig2` 建立上下文

## 6. 本项目当前参数语义（探针相关）

只保留以下参数：

1. `SyncProbePhaseBDelayMs`：
   - NewMap 到 PhaseB 的延迟
   - `0` 表示 `2 * Block_interval`
2. `SyncProbeSettleMs`：
   - PhaseA 后、NewMap 前等待入池
   - `0` 表示 800ms
3. `SyncProbeMaxAccounts`：
   - 每轮探针账户数

已删除旧参数 `SyncProbeDelayMs`，避免歧义。

## 7. 实验迭代流程范式（推荐固定执行）

本项目建议采用统一的闭环流程：

```text
运行实验 -> 发现异常/波动 -> 定位与调试 -> 最小修复 -> 同参数复跑 -> 清理调试产物 -> 更新文档结论
```

### 7.1 每轮最小动作清单

1. **运行实验**：明确本次唯一目标（例如“验证 window=200 在 4x4 是否闭环稳定”）。
2. **发现异常**：只记录“可复现症状”，不要先下结论。
3. **定位调试**：优先做最小可证伪改动（日志或条件分支），避免大改并行。
4. **最小修复**：一次只改一个核心点，保证因果可解释。
5. **同参数复跑**：使用与异常轮次一致的参数做 A/B 对照。
6. **清理调试产物**：删除 `results/debug_*`、临时 `outRoot`、重复指标 JSON。
7. **更新文档**：把“问题->修复->复验结果->剩余风险”写入实验文档与本指南。

### 7.2 何时判定“修复有效”

- 至少满足：
  - 同参数复跑 `>=2` 轮；
  - `probe_ok` 连续通过；
  - `abort,delta=0`；
  - 关键闭环计数（`ack_send/ack_recv`）与目标账户数一致或可解释。
- 若仅单轮通过，不标记“已修复”，标记为“候选修复”。

## 8. 每次问题响应的执行规范（与对话协同）

为保证“提问->行动->可验证结果”闭环，建议固定按下面节奏：

1. **先复述目标**：本轮要回答哪个问题（例如“为什么 4x4 下 window=0 有波动”）。
2. **先跑最小验证**：先单窗口单轮冒烟，再扩大到矩阵。
3. **中间结果可见**：每次运行都输出“参数、目录、是否完成、关键指标”。
4. **出现异常立即转 debug**：暂停扩量，先查根因并做最小修复。
5. **修复后必须复跑**：至少一轮同参复现 + 一轮复验。
6. **回收临时数据**：确认后再删 fail/冗余 run，避免污染正式结果。

**删**：`run_status=fail` 的 raw/metrics；Exp1 同组合非 latest 的 PASS 重复轮；`results/debug_*`、`*_smoke`、临时 `OutRoot`、probe=3 冒烟数据。

清理后确认：正式路径仍可追溯，文档引用与实际目录一致。

## 10. 批量实验工程规范

### 入口与探针

| 脚本 | 实验 | 探针 | 默认规模 |
|------|------|------|----------|
| `run_exp1.bat` | 可扩展性 | **关** | 4/6/8 × speed 200/400/800 |
| `run_exp2.bat` | MVSS vs Delta | **开** | 4×4，probe=50 |
| `run_exp4.bat` | 以太坊负载 | **关** | 4×4，`BlockTransaction.csv` |
| `run_exp6.bat` | Delta 窗口扫参 | **开** | 2×2（默认）；4×4 设 `OUT_ROOT=results/exp6_scale_4x4_full/raw` |

Exp2 Delta 臂可复用 Exp6 的 `window_200` raw，不必重跑。

### 结果目录（只认 canonical）

```text
results/exp1_scaling/{raw,metrics,summary}
results/exp2_concurrency/{raw,metrics,summary}
results/exp4_eth_workload/{raw,metrics,summary}
results/exp6_sensitivity/{raw,metrics,metrics_recalc_v2}   # 2×2
results/exp6_scale_4x4_full/raw                            # 4×4 主结论
results/figures/{exp1,exp2,exp4,exp6}/
```

每 run 必有 `run_meta.txt` + `run_status.txt`（Exp1）；raw 下含完整 CSV 与 `client.out.log`。

### run 编号语义

`run1/run2/...` = **同参数下的重复试验**，不是修复批次。汇总时 Exp1 取各组合 **latest PASS**。

### 批跑保护

- 组合数 >5 需 `ALLOW_LONG_RUN=1`（Exp1/Exp6 bat 内置）。
- Exp1 bat：`%7` 可为 `dryrun` 或单个 speed；**勿用 `%10`**（cmd 会误解析为 `%1+"0"`），多 speed 用环境变量 `INJECT_SPEED_LIST`。
- 跑前脚本会清残留 `go` 进程；Exp1 超时后也会清理。

### 验收口径（批跑）

| 实验 | PASS 条件 |
|------|-----------|
| Exp1/4 | `run_status=pass` 且 `tx_committed >= MaxInjectTxs`；探针关 |
| Exp2/6 | sync 闭环 + `abort,delta=0` + `probe_ok` |
